# 技术选型工作流：后续性能优化边界

## 会修改的内容

- `selection_evidence.py`
  - 首轮证据归属改为一次紧凑模型调用；只有证据超过阈值时才分批。
  - 第二轮继续只评估新增证据，不重复评估已有证据。
  - 将同一来源的多个“候选方案 × 指标”补检索缺口合并为一个任务，最多保留本地技术包和联网制造包两个任务。
  - 技术选型检索使用更短的文档相关性评分输入。

- `selection_decision.py`
  - 候选评分、风险分析和推荐审核只接收压缩后的决策证据卡，而不是完整证据正文。
  - 决策证据卡保留证据 ID、候选方案、指标、来源、标题和相关摘录；评分与风险仍引用原始证据 ID。

- 配置与测试
  - 增加证据卡长度、首轮单批阈值、补检任务合并和紧凑评分输入的配置与回归测试。
  - 记录各阶段耗时、评估批次和补检任务数，用于确认优化是否生效。

## 不会修改的内容

- 不修改技术选型图的节点名称、节点数量、边、入口、出口、条件路由或执行顺序。
- 不修改 `query_router_graph.invoke({"query": ...})` 的调用方式或公开返回结构。
- 不修改普通 RAG 工作流及其 `max_transform_count=2`；技术选型仍保持独立的一次本地查询改写预算。
- 不将检索任务中出现的候选方案或指标直接认定为“已被证据支持”；证据归属仍需经过模型判定。
- 不在证据不足时输出无依据推荐；仍返回 `insufficient_evidence` 或条件性结论。
- 不删除原始证据、图数据库数据、Milvus 数据或已有报告。
